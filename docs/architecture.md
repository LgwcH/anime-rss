# AniRSS 0.1 架构说明

本文记录仓库中 `0.1` 的实际实现边界，不是未来路线图。AniRSS 是单机桌面应用：没有远程服务、
Web 控制端、云账户或外部下载器进程。

## 组件概览

```text
┌────────────────────────── PySide6 桌面界面 ──────────────────────────┐
│ 概览 │ 订阅列表/内容详情 │ 下载任务 │ 设置 │ 系统托盘/通知         │
└──────────────────────────────┬───────────────────────────────────────┘
                               │ DesktopController 映射与 Qt 信号
┌──────────────────────────────▼───────────────────────────────────────┐
│                           AniRSSService                              │
│ 订阅保存/刷新 │ 首次基线/去重 │ 任务队列 │ 设置/自启动              │
└───────────────┬──────────────────┬───────────────────┬───────────────┘
                │                  │                   │
       ┌────────▼────────┐ ┌───────▼────────┐ ┌────────▼──────────────┐
       │ RSS/Atom        │ │ 命名与路径     │ │ DownloaderRouter      │
       │ urllib + XML    │ │ 规则与冲突编号 │ │ HTTP │ libtorrent 可选 │
       └────────┬────────┘ └───────┬────────┘ └────────┬──────────────┘
                └──────────────────┴────────────────────┘
                                   │
                    ┌──────────────▼──────────────┐
                    │ SQLite 状态库 │ 本地轮转日志 │
                    └─────────────────────────────┘
```

主要模块：

- `ui/` 构建概览、订阅、下载和设置四个页面，并负责托盘交互。
- `desktop_controller.py` 把 dataclass 转成界面使用的字典，接收服务事件并发出 Qt 信号。
- `core/service.py` 协调订阅、刷新、去重、任务状态和桌面设置。
- `core/feeds.py` 使用 Python 标准库获取并解析 RSS 2.x、RDF 风格 RSS 和 Atom。
- `core/downloaders.py` 提供内置 HTTP 下载器和按需导入的 libtorrent 下载器。
- `core/database.py` 使用 SQLite 持久化全部业务状态和设置。
- `core/scheduler.py` 在后台线程中检查到期订阅。
- `core/naming.py` 处理番剧目录、文件名清理、集数识别和单目录内的路径约束。
- `core/autostart.py` 维护当前用户级开机自启动项。
- `single_instance.py` 通过 Qt `QLockFile` 为每个应用数据目录提供跨进程所有权。

## 进程实例与生命周期

正式桌面入口会在打开 SQLite 前尝试取得数据目录中的 `anirss.instance.lock`。锁由
`SingleInstanceLock` 在控制器生命周期内持有，并在正常关闭或初始化失败时释放；`QLockFile`
负责识别记录进程已经不存在的遗留锁。若另一个存活进程正使用同一数据目录，新进程不会打开
数据库，而是提示已有实例并退出。锁的作用域是解析后的数据目录，因此不同 `--data-dir` 可以
各自运行一个实例；这不协调用户另行配置的相同媒体目标目录。演示模式不打开真实业务数据库，
也不取得该锁。

## 线程与事件

Qt 主线程只负责界面。手动“立即刷新”和详情中的“刷新此订阅”通过 Qt 线程池调用同步服务接口；
定时刷新由一个独立调度线程执行。下载使用 `ThreadPoolExecutor`，工作线程数量取自服务启动时的
“并发下载”设置。

服务事件可能从调度或下载线程产生。`DesktopController` 将事件转为 Qt 信号，界面随后重新读取
SQLite 视图；工作线程不直接操作 QWidget。下载进度约每增加 1% 持久化一次，以减少数据库写入。

修改并发数会写入数据库，但当前运行中的 executor 不会重建，因此重启应用后才能保证并发数完全
按新值运行。轮询间隔和其他供后续请求读取的设置无需迁移任务。

## 订阅流水线

一次刷新按以下顺序执行：

1. 订阅调度器根据 `last_checked_at` 和订阅/全局轮询间隔判断是否到期。首次订阅立即到期。
2. 同一订阅使用进程内锁串行刷新，避免手动刷新和调度刷新同时处理它。
3. 获取器只接受 HTTP/HTTPS，使用标准 TLS 校验、固定请求超时和可选 HTTP 代理；响应上限为
   10 MiB。
4. 解析前拒绝包含 DTD 或实体声明的 XML，再将 RSS/Atom 条目映射为统一 `FeedItem`。
5. 规则先检查标题：所有包含条件必须匹配，任一排除条件匹配则跳过。可选集数正则只负责提取
   `episode` 字段。
6. 磁力链接优先于 enclosure；没有磁力链接时使用明确的 enclosure，或识别条目内容中的
   `.torrent` 链接。普通文章链接不会自动成为 HTTP 媒体任务。
7. SQLite 以“订阅 + GUID”和“订阅 + 下载 URL”去重，并以一个 feed item 最多对应一个下载
   task 的唯一约束防止重复任务。需要自动入队时，feed item 与对应 task 在同一事务中写入；
   task 写入失败会一并回滚 item，使后续刷新仍能重试。
8. 若这是第一次成功刷新且 `download_existing` 为假，符合规则的当前条目只写入 `feed_items`
   作为基线。若该开关为真且自动下载已开启，现有可下载条目也会建任务。
9. 后续刷新只为数据库中第一次出现、自动下载开启且带下载 URL 的匹配条目建立任务。

成功刷新在条目处理完毕后更新最近检查时间。首次基线的判据仅是该时间仍为空：即使上一个进程
在首次刷新途中已经逐项写入一部分 feed item，只要尚未提交成功时间，恢复后的刷新仍会保守地把
整个来源作为首次基线。已写入项由唯一约束去重，默认策略下其余历史项也只进入基线而不会入队。
一次完整刷新并非一个覆盖所有条目的事务；原子边界是每个“需要下载的 feed item + task”对。

已有成功记录的订阅在失败时也会记录本次尝试；新订阅首次获取失败时则保留“尚未建立基线”的
状态，并由调度器的进程内最近尝试时间避免紧密循环。失败后等待正常轮询间隔，但重启应用会丢失
这份进程内失败尝试时间。0.1 没有自动重试、随机抖动或指数退避。获取器也不保存
ETag/Last-Modified，因此每次刷新都重新获取完整订阅文档。

“立即刷新”会依次尝试全部已启用订阅。单个源失败不会阻止后续源被检查，批次完成后界面会报告
本次存在失败。点击订阅进入二级详情后，界面从 `feed_items` 读取最近 300 条并与该订阅任务按
`feed_item_id` 合并；搜索、筛选和简介显示不会重新请求网络。

用户对具体条目点击下载时走独立的手动入口，不修改自动刷新语义。服务先取得与刷新、换源和删除
共用的订阅锁，锁内重新校验条目归属和下载地址，再按当前设置推导目录、文件名与下载类型。界面
不能传入任意 URL、目标路径或文件名。手动操作只绕过自动下载开关及标题过滤，仍受安全路径、
同目录文件名预留和 `feed_item_id` 单任务唯一约束保护；已有暂停、失败或取消任务复用原任务恢复。

## 路径与命名

每个订阅有两种目标方式：

- `save_directory` 为空时，在全局 `download_root` 下用安全化后的番剧名称创建一个子目录；重名
  订阅会自动追加编号。
- 用户在订阅对话框中选择绝对目录时，直接把该目录作为该订阅目标；它可以位于全局根目录之外。

文件名来自条目标题，并尽量保留下载 URL 的扩展名。命名层会清理路径分隔符、控制字符、Windows
设备名、尾随点/空格等；下载器再次验证最终文件只能位于该任务的目标目录内。同一目录已存在同名
任务、最终文件或 `.part` 文件时，服务会生成带编号的名称。

显式保存目录是用户直接授权的路径，而不是从 RSS 数据构造。AniRSS 不会让 RSS 标题覆盖该目录
选择，也不会自动搬迁已存在的媒体。

## 下载任务模型

持久化状态为：

```text
queued → downloading → completed
   │          ├──────→ paused → downloading/queued
   │          ├──────→ failed → queued（用户继续）
   └──────────└──────→ cancelled
```

应用关闭时，正在下载的任务会重新标记为 `queued`。下次启动创建下载线程池后，队列会重新提交。
“移除任务”删除 SQLite 元数据；HTTP 任务可由用户同时删除精确的最终文件和 `.part` 文件。BT 任务
可能包含多个文件或目录，当前实现拒绝自动枚举删除，以免误删同一番剧目录中的其他内容。

### HTTP 下载器

HTTP 下载器使用 `urllib.request` 流式读取：

1. 最终文件旁使用 `.part` 后缀保存未完成数据。
2. 如果 `.part` 已存在，发送 `Range: bytes=<现有大小>-`。
3. 只有响应状态为 `206` 且 `Content-Range` 严格匹配 `bytes start-end/total` 时才考虑追加。
4. `start` 必须等于本地 `.part` 大小，`end` 必须不小于 `start` 且小于 `total`；若响应带
   `Content-Length`，它还必须等于 `end - start + 1`。任一条件不符即报错，不向部分文件追加。
5. 服务器忽略 Range 并返回完整响应时从头覆盖 `.part`；根据 Content-Length/Content-Range
   计算进度，并要求最终已读字节数与已知总长度完全一致。
6. 完成后用同目录替换操作发布最终文件。

当前没有 HTTP 自动重试、分块校验、摘要校验或 ETag/Last-Modified 恢复元数据。断点续传只确认
服务器接受 Range，没有验证远端文件版本未改变。HTTP 下载限速字段存在于内部模型，但 0.1 界面
不提供相应设置，不应视为稳定的用户功能。

### libtorrent 下载器

种子或磁力任务在真正执行时才导入 `libtorrent`；导入失败只使该任务失败，不阻止应用和 HTTP
下载器启动。所有 BT 任务共享一个应用级 libtorrent session，各任务只创建独立 handle，并使用
自己的目标目录作为保存位置。共享 session 复用监听端口与 DHT 路由；退出时把有限大小的会话
状态原子写入数据目录的 `libtorrent.state`，损坏或版本不兼容时安全回退为新会话。

`.torrent` 文件先由 AniRSS 通过 HTTP 获取，限制为 20 MiB，再交给 libtorrent；磁力链接直接
交给 libtorrent 获取元数据。HTTP 代理只覆盖前一种 HTTP 获取，不配置 libtorrent 的 Tracker、
DHT、PEX 或 peer 流量。

任务达到完成状态后：

- “下载完成后继续做种”关闭时立即暂停并移除该 session 中的 handle；
- 开启时等待配置的分钟数，再暂停并移除；
- 磁力元数据超时或持续无数据时本次任务失败并释放工作线程，可由用户重试；
- 下载阶段仍可能发生 BT 上传；
- 没有分享率停止条件；当前持久化 DHT/session 状态，但不持久化逐任务 fastresume 数据。

监听端口和内部下载/上传限速值应用于共享 session；设置页暴露监听端口、元数据/无数据超时和按
分钟做种。

## SQLite 数据模型

一个 `anirss.db` 包含四类表：

- `subscriptions`：订阅地址、规则、保存目录、自动下载、首次刷新策略和最近检查时间；
- `feed_items`：已见 GUID、标题、下载链接、发布时间和提取的集数；
- `download_tasks`：来源、目标、文件名、类型、状态、字节数、进度和错误；
- `app_settings`：`AppSettings` 的 JSON 载荷。

仓库用一个 `sqlite3` 连接配合可重入锁在多个线程间串行访问，磁盘数据库启用 WAL、外键和事务。
自动下载路径通过单个事务插入 feed item 与 task，避免只留下“已见但没有任务”的半提交状态；
不需下载的条目仍单独写入。整个订阅文档不是单个事务。当前 schema 版本为 2，并包含少量针对
早期 0.1 开发数据库的就地加列迁移；没有通用配置导入器、降级器或只读恢复界面。

数据目录还包含轮转 UTF-8 日志、`libtorrent.state` DHT/session 缓存；运行中的桌面实例还持有
`anirss.instance.lock`。日志单文件上限约 2 MiB，最多 3 个备份。0.1 不提供诊断包导出或远程上传。数据库和日志均依赖
操作系统用户权限保护，不做应用层加密。

## 开机自启动

自启动适配器不调用 shell，只注册当前用户：Windows 使用 HKCU `Run`，macOS 写用户
LaunchAgent，Linux/其他 freedesktop 桌面写 XDG Autostart。关闭开关只移除以 AniRSS 标识创建的
条目。0.1 不请求提升权限，也没有启动延迟或启动时最小化的界面设置。

## 安全边界与当前限制

当前实现提供的边界：

- RSS 正文最大 10 MiB，种子元数据 HTTP 响应最大 20 MiB；
- RSS XML 拒绝 DTD 和实体声明；
- RSS 地址只允许 HTTP/HTTPS，HTTPS 默认验证系统信任链；
- 自动生成的目录/文件名经过清理，最终 HTTP 文件限制在任务目标目录内；
- 下载的内容不会被自动执行、挂载、解压或安装；
- libtorrent 缺失不会关闭 HTTP 功能。

0.1 尚未提供或保证：

- OPML 导入/导出、保存前订阅测试、规则试运行或独立人工确认候选队列；
- RSS 条件请求、HTTP/RSS 自动重试、错误退避或 HTTP 限速界面；
- 远端文件版本验证、内容哈希验证或通用下载完整性证明；
- BT 分享率停止、BT/SOCKS 代理或逐任务 fastresume；
- 远程控制、诊断导出、云同步、多用户隔离或凭据库集成。

私人 RSS URL、代理凭据和下载链接会以明文形式保存在本地 SQLite 中。部署者应依赖操作系统账户
权限保护应用数据目录，并在提交错误报告前自行检查数据库和日志。

## 测试范围

当前自动化测试覆盖 RSS/Atom 解析、路径命名、SQLite CRUD/去重、feed item 与任务的事务回滚、
HTTP 原子完成和严格范围续传、BT 元数据适配、首次基线的部分写入恢复、手动单条下载的并发幂等
与归属校验、任务文件移除、同数据目录单实例、当前用户自启动、桌面控制器映射及订阅详情导航。
libtorrent 是可选依赖，基础测试在没有它时仍可运行；仓库测试不应访问公网。
